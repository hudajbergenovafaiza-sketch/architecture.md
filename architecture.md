# Архитектура веб-системы управления заявками на пошив униформы

> **Стек технологий:** React (Vite) + Node.js + Express + PostgreSQL + Prisma.  
> **Цель проекта:** Автоматизация приёма, обработки и контроля выполнения заказов на пошив униформы, замена ручного учёта (тетради, мессенджеры) на единую цифровую систему.

---

## 1. Пользователи и роли

В системе предусмотрено 3 основные роли с разным уровнем доступа:

1. **Гость (Клиент без регистрации)** — посетитель сайта.  
   * **Что может делать:** заполнять и отправлять заявку на пошив (с указанием параметров и прикреплением файлов), проверять статус существующей заявки по её номеру и контактным данным.
2. **Сотрудник (Менеджер / Мастер)** — работник предприятия.  
   * **Что может делать:** просматривать общий список всех заявок, открывать детали заказа, изменять статус заказа в соответствии с производственным процессом (*«Новая» → «На рассмотрении» → «В обработке» → «В производстве» → «Готова» → «Выдана»*), просматривать загруженные клиентом файлы.
3. **Администратор** — руководитель или IT-специалист предприятия.  
   * **Что может делать:** имеет все права сотрудника, а также может управлять учетными записями сотрудников, назначать конкретных сотрудников на выполнение заказов и проставлять/изменять итоговую стоимость заказа вручную.

* **Почему так:** Разделение прав защищает внутренние данные компании и заказы от случайного или намеренного удаления клиентами. Если дать клиенту права сотрудника, он сможет менять статусы чужих заказов.

---

## 2. MVP (Минимально жизнеспособный продукт)

**MVP** (minimum viable product — минимально жизнеспособный продукт, самая первая рабочая версия) включает только самые необходимые функции для запуска системы.

### Что входит в MVP:
1. **Форма создания заявки** для клиента (параметры одежды, количество, загрузка файла, контакты).
2. **Авторизация сотрудников и администратора** по логину и паролю (для защиты панели управления).
3. **Панель управления (Dashboard)** для сотрудников со списком заявок и фильтрацией по статусам.
4. **Изменение статуса заказа** сотрудником.
5. **Ручной расчет и установка стоимости** администратором/менеджером после рассмотрения заявки.
6. **Назначение сотрудника** на конкретный заказ администратором.
7. **Страница проверки статуса заявки** для клиента (по номеру заявки).

### Что НЕ входит в первую версию и почему:
* *Онлайн-оплата заказов (банковской картой)* — слишком сложно для старта, требует подключения платежных шлюзов (ЮKassa, Сбер и т.д.) и договоров с банком.
* *Личный кабинет клиента с историей заказов* — клиенты оформляют заявки разово или редко, поэтому для MVP достаточно проверки статуса по номеру без пароля.
* *Автоматический расчет стоимости по сложным прайс-листам* — цены зависят от индивидуальных договоренностей и нестандартных тканей, поэтому ручная установка цены менеджером проще и надежнее на первом этапе.

## 3. Пользовательские истории (User Stories)

1. **Как гость**, я хочу заполнить форму заявки с параметрами одежды, чтобы заказать пошив униформы без обязательной регистрации. *(Входит в MVP)*
2. **Как гость**, я хочу прикрепить файл с макетом логотипа или размерной сеткой, чтобы швейное предприятие учло все детали. *(Входит в MVP)*
3. **Как гость**, я хочу узнать статус своей заявки по её номеру, чтобы понимать, на каком этапе находится мой заказ. *(Входит в MVP)*
4. **Как сотрудник**, я хочу войти в систему по логину и паролю, чтобы получить доступ к панели управления заказами. *(Входит в MVP)*
5. **Как сотрудник**, я хочу видеть список всех поступивших заявок в виде таблицы, чтобы ничего не пропустить. *(Входит в MVP)*
6. **Как сотрудник**, я хочу открыть подробную информацию по конкретной заявке, чтобы изучить требования клиента. *(Входит в MVP)*
7. **Как сотрудник**, я хочу изменять статус заявки (*«Новая» → «На рассмотрении» → …*), чтобы отражать реальный прогресс работы. *(Входит в MVP)*
8. **Как администратор**, я хочу проставлять итоговую стоимость заказа после его рассмотрения, чтобы клиент знал цену. *(Входит в MVP)*
9. **Как администратор**, я хочу назначить конкретного сотрудника на выполнение заказа, чтобы распределить нагрузку в цехе. *(Входит в MVP)*
10. **Как администратор**, я хочу создавать и удалять учетные записи сотрудников, чтобы управлять доступом к системе. *(Входит в MVP)*
11. **Как сотрудник**, я хочу фильтровать заявки по статусу или дате, чтобы быстро находить нужные заказы. *(В будущем)*
12. **Как клиент**, я хочу видеть историю своих заказов в личном кабинете, чтобы повторить удачный заказ. *(В будущем)*

## 4. Бизнес-правила

1. **Правило статусов:** Менять статусы заявок могут только пользователи с ролью «Сотрудник» или «Администратор». Клиент может только создать заявку.
   * *Почему нельзя проверять только в браузере:* Злоумышленник может открыть консоль разработчика в браузере или отправить прямой HTTP-запрос (через Postman) на сервер и изменить статус чужого заказа на «Выдана». Сервер обязан проверять токен пользователя и его роль.
2. **Обязательные поля заявки:** Заявка не может быть создана без указания типа униформы, количества и контактного телефона.
   * *Почему нельзя проверять только в браузере:* Пользователь может отключить JavaScript или обойти клиентскую валидацию (проверку формы в браузере) и отправить пустые данные, которые сломают базу данных.
3. **Безопасность паролей:** Пароли сотрудников никогда не хранятся в открытом виде — только в виде хэша (зашифрованной строки).
   * *Почему нельзя проверять только в браузере:* Если база данных будет скомпрометирована (взломана), злоумышленник получит реальные пароли сотрудников и доступ к другим сервисам, если они используют одинаковые пароли.

## 5. База данных

Для работы используется **PostgreSQL** и инструмент **Prisma** (ORM — программа-посредник между кодом Node.js и базой данных, позволяющая писать запросы на понятном языке JavaScript).

### Таблицы, поля и типы

1. **`Role`** (Роли пользователей)
   * `id`: Int (Primary Key — главный уникальный ключ)
   * `name`: String (Название роли: `admin`, `employee`)

2. **`User`** (Сотрудники и администраторы)
   * `id`: Int (Primary Key)
   * `email`: String (Уникальный логин/почта)
   * `password`: String (Хэш пароля)
   * `fullName`: String (ФИО сотрудника)
   * `roleId`: Int (Foreign Key — связь с таблицей `Role`)
   * `createdAt`: DateTime

3. **`Order`** (Заявки на пошив)
   * `id`: Int (Primary Key)
   * `orderNumber`: String (Уникальный номер заявки для клиента, например, "ORD-2026-001")
   * `clientName`: String (Имя клиента)
   * `clientPhone`: String (Телефон клиента)
   * `clientEmail`: String (Почта клиента)
   * `uniformType`: String (Тип униформы)
   * `size`: String (Размер)
   * `height`: String (Рост)
   * `color`: String (Цвет)
   * `fabric`: String (Тип ткани)
   * `quantity`: Int (Количество изделий)
   * `hasLogo`: Boolean (Нужен ли логотип: true/false)
   * `status`: String (Текущий статус заказа: `NEW`, `REVIEWING`, `IN_PROGRESS`, `PRODUCTION`, `READY`, `COMPLETED`)
   * `totalPrice`: Float? (Итоговая цена, изначально пустая `null`, пока менеджер не заполнит)
   * `assignedEmployeeId`: Int? (Foreign Key на `User`, кому назначен заказ)
   * `createdAt`: DateTime

4. **`OrderFile`** (Файлы к заявкам)
   * `id`: Int (Primary Key)
   * `orderId`: Int (Foreign Key на `Order`)
   * `filePath`: String (Путь к файлу на сервере или в облаке)
   * `fileName`: String (Оригинальное имя файла)

### Связи между таблицами
* **`Role` и `User`**: Один-ко-многим (у одной роли может быть много пользователей, но у пользователя только одна роль).
* **`User` и `Order` (assignedEmployee)**: Один-ко-многим (сотрудник может выполнять много заказов, у заказа один ответственный сотрудник).
* **`Order` и `OrderFile`**: Один-ко-многим (у одного заказа может быть несколько прикрепленных файлов).
